Router accuracy at scale

A 3-tier cascade router (regex heuristic → pgvector nearest-neighbour → Haiku LLM classifier) is evaluated against a 67-query labelled set spanning four categories. The router decides which downstream model serves each model: "auto" request — cheap tiers handle what they can, expensive tiers see only what they must.

The single misroute

Query #33 — code predicted as fast-qa

"Explain in plain English what this Python decorator does — no code edits needed: @lru_cache(maxsize=128)"

Tier fired: llm (confidence 0.95). The "plain English, no code edits" framing pulls the classifier toward fast-qa, even though the subject is a Python construct. This is the polarity-edge query the eval set deliberately includes to stress-test the boundary — the misclassification is genuinely arguable, since a one-sentence English explanation is the kind of answer a fast-tier model can give well.

Methodology & caveats

What ran

scripts/run_router_eval.py --threshold 0.45 against eval/router_eval.yaml (67 queries) inside the gateway container, with the production embedding model (sentence-transformers/all-MiniLM-L6-v2) and production tier-3 classifier (claude-haiku-4-5). Embedding threshold 0.45 is the locked production default per the v3.3 threshold sweep.

What did not run

The threshold sweep was not re-run for this report — the existing sweep artifact at eval/results/2026-06-17_router_threshold_sweep.json is current and was used to set 0.45 originally.

Known limits of this number

The 67-query eval set is hand-curated to cover the four target categories and several deliberate edge cases; it is not a sample from production traffic. Accuracy on real traffic will diverge as user phrasing distribution shifts. The router latency p95 (~1.4 s) exceeds the original spec target (<100 ms) — that target was set against a heuristic-only design; the production cascade trades latency for accuracy by design.
