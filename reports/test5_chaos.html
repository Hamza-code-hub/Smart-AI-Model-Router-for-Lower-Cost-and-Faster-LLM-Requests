Resume bullet

Mapped fail-soft behavior end-to-end under synthetic infra outages: a docker pause of Redis degraded all 5 in-flight requests to 200 (cache + token-bucket rate-limit fail open, p50 latency climbed from 1.9 s to 6.5 s as every call missed cache), and recovery to baseline took under 2 seconds. A Postgres pause, by contrast, blocked the request path entirely (0/5 served inside a 15-second client deadline) — an honest finding contradicting the design intent. Cross-provider failover policy is wired (FAILOVER_STATUS_CODES = {408, 425, 429, 500, 502, 503, 504} at src/gateway/fallback.py:15) and per-target circuit-breaker state is observable via /admin/breakers (all 4 targets closed, 0 failures).
Honest finding — Postgres is a hard dependency. The plan called this scenario as “200s during outage; logging degrades silently.” The measurement disagrees: with Postgres paused, all 5 requests timed out at the 15-second client cutoff with no HTTP response. The most likely culprits are the synchronous tenant key-lookup, semantic-cache check, and request-log write on the request path; one or more of these does not catch and degrade. Wrapping the Postgres path in a per-call timeout with a fail-open default is tracked in future_work.md.

Methodology

Four scenarios. 5a/5b — baseline call, docker pause <svc>, 5 calls during the outage, docker unpause, recovery call. Same request body in every call (model: "auto", single user message) so any latency change is attributable to the paused dependency, not the workload. Tenant: default (rate limit 600 RPM). Curl per-call timeout: 15 s.

5c — queried the requests table for historical fallback_used = true rows. This is a passive measurement of failover in production traffic; the failover code path itself is proved by reading src/gateway/routes/chat.py:178–234, where every provider exception passes through should_failover() and on a match the next target in the cascade is tried.

5d — GET /admin/breakers with the admin bearer. Returns one entry per (provider, model) pair under management with state and failure count. Raw logs: eval/results/resume_run/test5{a,b,c,d}_*.log.

In 1,081 logged requests, no upstream returned a status the policy classifies as failover-eligible. Honest read: the policy is wired and observable, but it has not been exercised in production — we cannot claim a measured MTTR for this scenario.

Failover policy (source)

# src/gateway/fallback.py
FAILOVER_STATUS_CODES = frozenset({
    408, 425, 429, 500, 502, 503, 504,
})

def should_failover(exc: ProviderError) -> bool:
    return exc.status_code in FAILOVER_STATUS_CODES
Used at src/gateway/routes/chat.py:178–234: on a provider exception, the policy decides whether to advance to the next target in the cascade. Deterministic 4xx (e.g. 401, 400) are deliberately not retried — retrying a malformed request just wastes budget.

What I would do with another week

  • Wrap the Postgres call sites on the request path (tenant key-lookup, semantic-cache check, request-log write) in per-call timeouts with explicit fail-open defaults, then re-run 5b. The expected result is the same Redis-style behavior — 5/5 200s during the outage at degraded p50 latency.
  • Engineer a failover event end-to-end by injecting an invalid ANTHROPIC_API_KEY at process-env level on a single request and measuring time-to-OpenAI in the response trace. Today's evidence (zero fallback_used = true rows in 1,081 calls) shows the policy is untriggered, not that it works.
  • Add a synthetic chaos cron job (weekly): pause Redis for 30 s, pause Postgres for 30 s, kill the gateway pod — emit a Prometheus alert if recovery exceeds the target SLO. This turns a one-shot measurement into a regression test.
  • Surface breaker state in the public /health body (today it's admin-only) so load balancers can drain a gateway instance whose downstream is flapping.
