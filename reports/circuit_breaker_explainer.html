Circuit Breaker

Why we stop calling a degraded provider — and how we know when to start again.
The breaker sits between the failover loop and the actual provider call. When a target accumulates enough recent failures, it trips: future requests skip that target without touching the network. After a cooldown, one probe call is allowed through — success closes the breaker, another failure re-opens it for the full duration.

Trip conditions

# src/gateway/breaker.py:22–24
FAILURE_THRESHOLD      = 5
FAILURE_WINDOW_SECONDS = 30.0
OPEN_DURATION_SECONDS  = 60.0

record_failure(provider, model) at breaker.py:78–102:

  1. Prune the entry's failure-timestamp list to entries inside the last 30 s.
  2. Append now.
  3. If len(failures) ≥ 5 and state is CLOSED → flip to OPEN, log breaker.opened.
“5 failures in any rolling 30-second window” — a burst of 5 in 2 s trips it; one failure every 7 s for 5 minutes does not, because older timestamps age out of the window before the count reaches 5.
A failure while HALF_OPEN bypasses the threshold entirely: one bad probe re-opens immediately and resets the cooldown to a full 60 s (breaker.py:82–88). No second chances.

The half-open dance — a timeline

During the OPEN band, every failover-loop iteration that asks for this target gets allow() = False and continues straight to the next target. The breaker is not a queue — it is a gate.

What counts as a failure

The breaker only records failures that the failover policy considers worth retrying. From src/gateway/routes/chat.py:382–383: 

except ProviderError as exc:
    if should_failover(exc):
        breaker.record_failure(target.provider, target.model)
Status codeCounts toward trip?Why
408, 425, 429yesTimeout / rate-limited — transient. Likely to recover; worth backing off.

Failover policy and breaker share the same should_failover() predicate. They are deliberately coupled: if it is not worth retrying on the other provider, it is not worth counting toward the trip threshold either.

How the request path uses it

The breaker gate runs before the provider call. If the gate is closed for that target, the loop skips it entirely — no socket opened, no token spent. 

# src/gateway/routes/chat.py:368–397 — non-streaming path

        logger.info("chat.breaker_skip", provider=target.provider, model=target.model)

    breaker_blocked_all = False

    try:
        response = await provider.complete(request, target.model)

        if i < len(targets) - 1 and should_failover(exc):

Same breaker logic, plus the “peek the first chunk” pattern so a provider that returns non-200 on the first event becomes a clean failover — not a half-sent stream.

The “all breakers open” case

The breaker_blocked_all flag (chat.py:366, 372) tracks whether any target in the cascade got a real attempt. If every target was breaker-blocked, the request never touched a provider — that is a different failure mode from “we tried, they all 503’d” and the gateway returns a distinct error so ops can tell them apart.

Honest caveat — single-node only

From breaker.py:9–11: “In-memory, single-node only (matches the spec’s v2 assumption). A multi-node deployment would need Redis-backed state, but a hobby gateway doesn’t.”

Each gateway process has its own _entries: dict[(provider, model), _Entry] guarded by a threading.Lock. With one instance this is correct and fast. With N instances behind a load balancer, each holds an independent opinion of Anthropic’s health — one might be tripped while another is hammering away — and the effective trip threshold is 5 × N.

A multi-node port would push failure timestamps into Redis, similar to how the rate-limit token bucket already does. For now: single node is the assumption; this is a known boundary, not a bug.

How the three resilience layers stack together

LayerLives inDecides
Failover policy fallback.py Which errors are worth retrying on a different provider, and the order of targets to try.
Streaming swap-before-bytes _stream_with_failover When a swap is still safe during a streaming response (always before the first downstream byte).
Circuit breaker breaker.py Whether to even try a target right now, based on its recent failure history.

Each request walks all three: breaker decides if the target gets an attempt → failover policy decides what to do on error → streaming peek decides whether the swap is still safe. Test 5 verifies them as separate sub-tests (5a/b chaos, 5c failover, 5d breakers) because they fail independently and should be reasoned about separately.
