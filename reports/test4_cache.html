Resume bullet

Built an exact-match Redis cache (SHA-256 fingerprint of model + system + messages + temperature, 24 h TTL, temperature gate at 0.3) that delivered a 100% hit rate on a 10-prompt repeat workload, collapsing p50 latency from 961 ms to 3 ms (320× speedup, 99.7% reduction) and zeroing out provider cost on cached requests. Cache key is deterministic; cached responses set cached: true on the body for downstream observability.
Honest caveat — semantic cache. The handoff plan called for a pgvector semantic cache to hit lexically-different paraphrases at threshold 0.95. The schema is provisioned (semantic_cache_entries table from the Phase 2.2 migration) but the lookup path is not yet wired into the request handler — grep finds zero Python references to the table. The cold pass below shows 0% hit rate on paraphrase pairs as a result: every paraphrase fell through to the Anthropic Haiku call. That is a real measurement of the current build, not a regression. Wiring the semantic-cache lookup is tracked in future_work.md.

Methodology

Workload: eval/workloads/paraphrase_cache.yaml — 10 prompts, split into two groups of 5. Group A (pc-a*-prime) is the prime set; Group B (pc-b*-para) is a paraphrase of each Group A item (e.g. “What is the capital of France?” ↔ “What's the capital city of France?”). All routed through the fast-qa virtual model → claude-haiku-4-5, temperature=0, max_tokens=80.

Pass 1 (cold) — cleared semantic_cache_entries via DELETE FROM semantic_cache_entries WHERE route_key='fast-qa', then ran the full 10-prompt workload. This measures: (a) cold-path latency for the prime calls, and (b) whether the planned semantic cache fires on the paraphrases. Pass 2 (warm) — re-ran the same 10 prompts immediately, with the exact-match Redis cache primed by Pass 1.

On a cache hit, the gateway returns the stored ChatCompletionResponse without invoking any provider, so provider cost is exactly zero. The eval reporter still echoes prompt/completion tokens for downstream accounting, but no provider request is made — verifiable via the cached: true field on each row of test4_paraphrase_cache_pass2.json.

Why paraphrases didn't hit in Pass 1

The exact-match cache keys on a SHA-256 of virtual_model + system + json(messages) + temperature. Any lexical change to the user message produces a different key. So: 

pc-a1-prime  "What is the capital of France?"        → key A
pc-b1-para   "What's the capital city of France?"     → key B  (different)
pc-a1-prime  (re-sent in pass 2, byte-identical)      → key A  (HIT)

A semantic cache — embed the user message with MiniLM-L6-v2, ANN-search against a pgvector HNSW index of prior queries at cosine > 0.95, return the stored response if found — would let paraphrases of the same question reuse the same answer. The DB schema for this exists (semantic_cache_entries) but the lookup code is not yet checked into src/gateway/cache/.
